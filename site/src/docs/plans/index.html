Plan files

A plan file is a test you want to run again. It holds the same commands a tester would type, and runs every case in one go with no AI turn per step.

Example

This plan ships with the repo as examples/settings.plan and works on any Android device.

app com.android.settings
name settings-example

flow home
  launch --restart
  wait "Search Settings" --timeout 15
end

case TC-01 "Network & internet opens"
  run home
  tap "Network & internet"
  check "Internet"
  key back
  check "Search Settings"

case TC-02 "Search finds Wi-Fi settings"
  run home
  tap "Search Settings"
  retry 2
    type "wifi" --into id=open_search_view_edit_text --clear
    wait "~Wi-Fi" --timeout 5
  end
  check "~Wi-Fi"
./tnazar run examples/settings.plan

Syntax

LineMeaning
app <package>The app under test. Required.
name <run-name>Run name. Defaults to the file name.
source "Spec name"Optional, at the top: the spec the requirements come from (a PRD, a user story).
requirement R1 "Text"Optional, at the top: one thing the feature must do. --source "§2.4" says where in the spec; --out-of-scope "why" leaves it untested on purpose. See Requirements.
approved <fingerprint>Written by ./tnazar plan approve after you agree to the requirements. Never write it by hand.
case TC-01 "title"A test case. It runs until the next case, flow or the end.
flow <name> … endA reusable block, used with run <name>.
retry N … endRepeat until every step inside passes, up to N times.
if "Text" … else … endBranch on what is on screen. Never fails the case.
expect "Text"Optional, at the top of a case: an expected result, E1, E2… in order. Each one needs a check … --for E1 in that case, or the plan is refused. --req R1 says which requirement it proves.
check "Text"A verification. --for E1 links it to an expected result; a linked check that never ran leaves its case blocked, by name.
require "Text"The state the setup must reach (a fresh chat, a logged-in home). If it does not hold, the case stops as blocked · precondition not met: the app was never tested, so it never fails.
# commentIgnored, on a line of its own. Indentation is for people.

The whole file is checked before anything runs, so a typo never reaches the device. Secrets go in as --env NAME, never as values.

Have your test cases in a sheet? ./tnazar cases import cases.csv --app <app> writes a draft plan with every case, its ID and its expected results; ./tnazar plan review plans/cases.plan lists what is still missing. A run refuses the draft until every expected result has a check.

Every selected case is in the report. If the run stops early (an error, --stop-on-fail), the cases after it are listed as not run with the reason, and the summary ends with verified N/M.

Requirements: is the whole feature tested?

Six passing cases do not prove a feature works if none of them tested the rule that matters. Give Teesri Nazar the spec, and the agent lists what the feature must do as requirements at the top of the plan, then links each expected result to the requirement it proves.

source "Transfer PRD v3"
requirement R1 "A valid amount transfers and shows a reference" --source "§2.1"
requirement R2 "A second tap on Pay creates no second transfer" --source "§2.4"
requirement R3 "Daily limit resets at midnight" --source "§3.2" --out-of-scope "needs a clock change"

case TC-01 "Transfer"
  expect "Reference number shows" --req R1
  ...
  check "~Reference" --for E1
  1. ./tnazar plan review plans/transfer.plan lists every requirement with its source and the expected results that prove it. One that nothing proves shows as NOT COVERED.
  2. You read the list. When you agree, ./tnazar plan approve plans/transfer.plan records a fingerprint of it. If a requirement, its source or what proves it changes later, the report says so.
  3. The run reports requirements 4/5 verified next to the case results, and names each requirement that is not covered, not verified or failed.

A requirement is verified only when every expected result linked to it was proven and its case passed. A plan with requirements exits 1 until the list is approved and every requirement in scope is verified, so a green CI job means the feature was tested, not only the cases someone thought of. Plans without requirements work as before.

Exit codes

Every command, run, flow and replay use the same codes, so CI can act on them.

CodeMeaning
0OK. For run and replay, every case passed, and, in a plan with requirements, every requirement in scope is verified.
1Failed: a check failed or an element was not found. In a plan with requirements, also when one is not covered or not verified, or the list was never approved or changed since.
2Error: a bad plan line or a setup problem. Nothing was tested.
3Held: you sent a dashboard message. Continue with --from <case>.
4wait A --or B saw B instead of A.
5Still paused from the dashboard after 60 s.
