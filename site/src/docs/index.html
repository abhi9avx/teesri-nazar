Quick start

You need:

  • adb (Android platform-tools) on your PATH, or ANDROID_HOME set.
  • A phone with USB debugging allowed, or a running emulator. adb devices should list it.
  • Python 3.9 or newer. Teesri Nazar uses the standard library only, so there is nothing to pip install.
  • Claude Code, with claude on your PATH.
git clone https://github.com/abhi9avx/teesri-nazar.git
cd teesri-nazar
cp .env.example .env                     # test PINs and OTPs, never logged
cp testdata.example.yaml testdata.yaml   # test accounts, environment, DB, Figma links
claude

Then ask for what you want tested, in your own words:

Open Settings and check that search finds Wi-Fi.

Claude plans the test cases, shows you the plan, runs them on the device and finishes with a report. Every run is saved in runs/<name>/; report.html is the one to share.

How a test runs

  1. Plan. Your input (free text, pasted test cases, a PRD, a Figma or Jira link) becomes numbered test cases with expected results. The agent adds the edge cases you missed and says what it will not test.
  2. Explore. It looks at just the screens the cases touch, to write exact selectors.
  3. Run. Every expected result is a check. A whole plan file runs in one command, with no model turn per step.
  4. Report. Pass, fail or blocked for each case, what it saw against what was expected, and a screenshot for every check.

The full design, from adb up to the report, is in ARCHITECTURE.md.

Commands

Claude runs these for you. You can also drive the device yourself.

CommandWhat it does
./tnazar start <name> --package <app>Start a test run
./tnazar observeShow what is on screen: elements with index, id, text and label
./tnazar tap "Pay now"Tap by text, or by id=, desc= or #index
./tnazar type --env APP_MPIN --into id=pinType a secret from .env without it ever being printed
./tnazar check "Payment successful"Verify something is on screen (exact; '~text' for partial)
./tnazar case start TC-01 "title"Group the next steps into a test case; case end closes it
./tnazar run plans/x.planRun every case of a plan file in one go
./tnazar goto "wi-fi"Go to a screen by a route learned in earlier runs
./tnazar mapWhat was learned about the app: screens, names, usable steps
./tnazar replay <name>Run a recorded test again, on the same or another device
./tnazar uiOpen the live dashboard
./tnazar stopFinish the run and write the report

Every command has --help.

Plan files

A plan file holds test cases you want to run again. Shared steps are flows, flaky steps go in retry, and every expected result is a check. This one ships with the repo and works on any Android device:

app com.android.settings
name settings-example

flow home
  launch --restart
  wait "Search Settings" --timeout 15
end

case TC-01 "Network & internet opens"
  run home
  tap "Network & internet"
  check "Internet"
  key back
  check "Search Settings"

case TC-02 "Search finds Wi-Fi settings"
  run home
  tap "Search Settings"
  retry 2
    type "wifi" --into id=open_search_view_edit_text --clear
    wait "~Wi-Fi" --timeout 5
  end
  check "~Wi-Fi"

Run it with ./tnazar run examples/settings.plan. Exit code 0 means every case passed, 1 that one failed.

The live dashboard

./tnazar ui starts a small server on 127.0.0.1 and opens it in your browser. You see the phone screen, a timeline of every step with how long it took, and a box to message the agent. You can pause the run, and hand over an OTP or PIN that the dashboard types into the device itself. Nothing is hosted or uploaded.

Limits

  • Android only, for now.
  • Flutter, WebView and canvas screens show little or nothing in the accessibility tree, so they are hard to test.
  • Jetpack Compose screens show no ids unless the app sets testTagsAsResourceId; taps fall back to labels and text.
  • Secure screens (PIN or card entry) come out black in screenshots. The element tree still works.
  • Typing is ASCII only, because adb types that way: no ₹, Hindi or emoji.
