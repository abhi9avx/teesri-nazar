How it works

Claude Code is the tester's judgement. tnazar, a small Python tool, gives it eyes and hands on the phone and writes down everything it does.

Two parts

PartJob
Claude Code (the agent)Reads your request, plans the cases, decides each next step, and judges what it sees. Its playbook is CLAUDE.md in the repo.
tnazar (the tool)Reads the screen, taps and types through adb, checks results, and records every step with a screenshot. There is no AI inside it.

The loop for every step

  1. Look. Read the screen's element tree: ids, labels, text and positions. About 0.05 s through the UiAutomator2 server when the device has it, about 2 s with uiautomator dump otherwise.
  2. Act. Tap, type or scroll on the right element.
  3. Check. Verify the expected result on screen, and in the DB or Figma when you give access.
  4. Record. Save the step, a screenshot and the result.

How it finds elements

No XPath. A target is matched in this order, so tests survive layout and screen-size changes:

  1. id: tap id=btn_pay
  2. accessibility label: tap desc="Navigate up"
  3. visible text: tap "Pay now", or '~Pay' for a partial match
  4. position, only when nothing else exists: tap 9%,6%

Pass, fail and blocked

  • A case passes when every check in it passed.
  • It fails when any check failed, or the app crashed or froze (ANR). Crashes are caught automatically.
  • It is blocked when it could not run, for example the environment was down. The reason is recorded.

It learns your app

Every run maps the screens it visits and the taps between them. Next time, tnazar goto "wi-fi" reaches a known screen in one command, checking each step. Money-moving steps such as pay, transfer and PIN screens are never replayed.

Replay

tnazar replay <run> runs a recorded test again, on the same or another device, and re-checks every UI result. DB and Figma checks from the original run show as notes.

Deep dive. The full design, from adb to the report, is in ARCHITECTURE.md.
